# 排障记录：中文拼音「只显示第一个字符」——三层叠加的假象

状态：已定位并修复（2026-10，决策与修复见 [ADR-033](../decisions/033-option-as-alt.md)）。
记录排查路径与可复用的诊断方法，供以后处理 gpui 输入/绘制类问题时参考。

## 现象

用中文输入法打拼音，只有第一个字母出现在终端里，后续字母不可见；
提交选词却正常。shell 里正常、pi（TUI 编辑器）里复现；kitty 终端里
跑 pi 也正常——一度指向「zhimaterm 特有」。

## 结论：三层独立缺陷叠出同一个假象

**第一层（IME 数据层，shell 与 TUI 都受影响）**：`TerminalView` 的 IME
契约自相矛盾——`marked_text_range` 声称存在组合区，`text_for_range`
却返回 `None`。输入法（鼠鬚管 inline_preedit）更新组合前要读组合区
现状来算替换范围，读到空就只发首字符。修复：组合串成为可读的虚拟
缓冲区（三个查询自洽）。

**第二层（绘制层，只有反相光标块的 TUI 受影响）**：数据修好后 pi 里
仍「只见首字符」。preedit 文字色取的是**光标格前景色**，TUI 的反相
光标块让该格前景恰好与界面底色同系——整串一直都在画，只是不可见；
第一个字符压在亮色光标块上才显出来。修复：颜色改用主题默认前景。

**第三层（绘制层，浅色主题下才显形）**：改用主题默认前景后，组合文本
不再整串隐形，但**第一个字符仍被吞掉**——这次是压在**深底**上。主题前景
是界面的默认前景，与组合文本脚下那一格的底色未必同系：pi 的假光标是反相
格（SGR 7，前景底色互换），浅色主题下那一格是深底浅字，主题前景（深色）
画上去等于没画。kitty 里同一段拼音正常，因为 kitty 的 marked text 是系统
用**终端自己的默认色**画的（实测黑底 #000000 + 浅字 #eeeeee），压根不落在
格子上。

最终规则：**组合文本是终端自己画的内容**——它自带一块不透明的底（终端默认
背景色），盖住应用画在那一格的东西（反相假光标、输入条底色、占位文字），
文字用终端默认前景色。配套按字形簇逐个折算占格（wcwidth）、逐簇钉回网格，
组合区的底按占格宽度铺。

「只显示第一个字符」在每一层各自都有一个似是而非的解释（输入法只发
一个字符 / 只画了一个字符），单独验证任何一层都会误判已修好。第三层的
教训：前两层的修复把「整串隐形」换成了「首字符隐形」，症状看着几乎没变
（还是只看得见后面几个字符），容易误判成没修好。

**三层的共同教训**：每一层都是「用了一个看起来相关的颜色/字段，其实是
另一个来源」。修的时候要问的不是「怎么让这次看得见」，而是「这个颜色/
位置本来就该从哪来」——问到来源，规则才是完整的，测试也才写得出来。组合
文本这一例的答案是：它既不属于界面（界面 token），也不属于应用（应用画在
那一格的文字），它是终端的内容，所以该用终端自己的默认色、自带底色。

## 排查路径（每一步的证据与结论）

1. **静态穷举**（事件派发 → `set_marked_text` 透传 → handler 适配 →
   绘制）：每一环都「看起来对」，产生不了新证据。教训：IME/绘制问题
   合成输入进不了 gpui 窗口，静态分析很快到头，尽早转运行时观测。
2. **IME 入口日志**（`replace_and_mark` / `replace_text` / `text_for_range`）：
   证明数据层每步整串更新、提交正确——排掉第一层，问题在下游。
   （注意：当时 shell 已被第一层修复治好，差一点就此误判收工——
   用户补充「pi 里仍有问题」才继续。）
3. **绘制日志**（`paint_preedit` 打 len + 锚点，`| uniq` 压缩）：
   证明每帧都拿到新文本在画——排掉「没画」，只剩「画了看不见」。
4. **红块暴露**（给 preedit 区铺红色背景 quad）：位置、宽度、整串
   一次定音，用户肉眼确认「红块随输入变长、字都在」→ 颜色问题。
5. **读 TUI 源码定案**（第三层）：pi 用 APC 序列标记自己的假光标
   （`pi-tui` 的 `FAKE_CURSOR_START`），绘制时套反相（SGR 7），再把硬件
   光标停在同一格并用 DECTCEM 隐藏，指望终端据此锚定输入法——组合文本
   于是正好落在那个反相格上。终端把反相格渲染成「深底浅字」，而组合
   文本用的是主题前景（深色），两者撞在一起，首字符就没了。

## 可复用的方法与教训

- **分层日志 + uniq 压缩**是 gpui 无头测试的替代：数据层（IME 回调）、
  绘制层（paint 入参）各打一行，配合管道 `| uniq` 只看变化。
- **给可疑绘制物铺显眼背景色**是绘制问题的终局手段：同时回答位置、
  尺寸、遮挡、图层顺序四个问题，比读渲染代码快得多。
- **gpui 的 IME 契约**：`text_for_range` 返回 `None` 但 `marked_text_range`
  返回 `Some` 是矛盾组合，输入法行为不可预期；实现 `EntityInputHandler`
  时两者必须自洽（参考本仓库 `ui/input/core.rs` 的真实缓冲区实现）。
- **死路记录**：「`accepts_text_input` 在 option 修饰时返回 false 绕过
  IME 优先分支」不可行——该标志同时控制 gpui 每帧的输入会话启停，
  置 false 会把中文输入整个关掉。
- **用户反馈要精确到场景**：「终端正常、pi 不行」「kitty 里都好」这类
  对照信息每一条都砍掉一半假设空间，比任何代码阅读都值钱。

## 2026-10-21 更新：状态机已可无头测试

终端侧组合状态机（组合串 + 选区 + UTF-16 协议钳制）提取为 `ui/input/ime.rs`
的 `ImeComposition`：三查询自洽、代理对不劈开、组合→扩展→改选区→提交/取消
的全部转移有单测守住；表单侧（core.rs）的组合转移（历史单步、只读闸门、
选区相对替换起点）同样补了无头测试。本文的排查手段仍适用于**窗口层**接线
（候选窗定位、焦点、渲染帧），但「状态机只能真人过」的结论自此只覆盖窗口层。
