# ssh-agent 图解:钥匙管家是怎么工作的

状态:概念说明 + 本项目相关设计决策的背景(2026-10)。面向不熟悉 SSH 内部机制的同学。

---

## 1. 先铺垫 30 秒:登录服务器有两种"证明我是我"的方式

```
方式一:登录密码 —— 把秘密告诉对方

   你 ──"我的密码是 xxx"──▶ 服务器
   ⚠ 秘密离开了你的电脑,服务器(和路上的窃听者)拿到了它

方式二:私钥签名 —— 用钥匙答题,不交出钥匙

   服务器 ──"来,把这段随机数签个名"──▶ 你
   你 ──(用私钥盖章)──▶ 服务器(用公钥验证盖章)
   ⚠ 私钥本身永远不离开你的电脑
```

- **公钥** = 一把锁,贴在服务器上(`~/.ssh/authorized_keys`),谁都能看。
- **私钥** = 配套的钥匙,只在你电脑上(比如 `~/.ssh/id_ed25519`)。
- 登录时服务器出一道"只有真钥匙才能答的题",你答对了就放行。

私钥文件本身为了安全,还有一个**口令**(passphrase)保护——注意这和登录密码是两回事,它是"打开私钥文件的口令"。接下来就轮到 agent 解决它的麻烦。

## 2. 没有 agent 的世界:每次都要开一次保险柜

```
┌─────────────────────────────────────┐
│  $ ssh server1   → 输入私钥口令 🔐    │
│  $ git push       → 输入私钥口令 🔐    │
│  $ ssh server2   → 输入私钥口令 🔐    │
│  $ scp file ...   → 输入私钥口令 🔐    │
└─────────────────────────────────────┘
   每个要用钥匙的程序,都来问你一遍口令
```

而且每个程序都要自己读私钥文件、自己解密——用你的身份跑的任何程序理论上都能碰到它。

## 3. agent 登场:一个常驻的"钥匙管家"

ssh-agent 是电脑里一个后台小服务,职责只有一件事:**替你保管私钥、代你盖章**。

```
第一步(只做一次):把钥匙交给管家

  $ ssh-add --apple-use-keychain ~/.ssh/id_ed25519
    Enter passphrase: ▓▓▓▓▓▓          ← 输一次口令
    Identity added                     ← 钥匙进入 agent 内存
    (口令同时存进 macOS 钥匙串,重启后自动恢复)

之后的每一天:

                 ┌──────────────┐
                 │  ssh-agent   │   钥匙管家(后台常驻)
                 │   🔑 🔑      │   钥匙只存在于它的内存里
                 └──────▲───────┘
            盖章请求 │ 返回盖章结果
        ┌────────────┼────────────┬─────────────┐
     $ ssh ...    $ git push   zhimaterm     其他程序

        (它们拿到的都只是"签名",谁都摸不到私钥本身)
```

日常体感:`ssh`、`git push`、打开 zhimaterm 连服务器——全部直接过,什么都不用输。

## 4. 关键机制:私钥不出门,出门的只是签名

需要证明身份时,流程永远是:

```
  程序(git/ssh/zhimaterm)          ssh-agent
        │                              │
        │  "服务器出了这道题,帮我签"    │
        ├─────────────────────────────▶│
        │                              │ 用内存里的私钥盖章
        │      "这是签好的结果"         │
        │◀─────────────────────────────┤
        ▼                              │
     把签名交给服务器验证               │
                                     钥匙从未离开这里
```

类比:私钥像一枚**公章**,agent 是拿着公章的**秘书**。任何部门要盖章,把文件递给秘书,秘书盖完把文件还回来——公章本身永远锁在秘书的保险柜里,没有任何人经手。

## 5. agent 转发:让服务器上的程序也能用你的管家

**场景**:你 SSH 登录到服务器 A,想在 A 上 `git clone`(SSH 方式)。A 上没有你的私钥,怎么办?

- ❌ 错误做法:把私钥文件拷到 A——私钥从此散落在每台登录过的机器上,安全隐患巨大。
- ✅ 正确做法:开 **agent 转发**。

```
     你的 Mac                              服务器 A
  ┌────────────────┐                ┌──────────────────────┐
  │  ssh-agent  🔑  │◀═══════════════│  你登录后的会话         │
  │  (钥匙不出门)   │   同一条 SSH    │                      │
  └────────────────┘   连接里往返     │  $ git clone git@…   │
                                    │      │               │
                                    │      ▼               │
                                    │  需要盖章 → 请求被送回  │
                                    │  你的 Mac,签好再传回来  │
                                    └──────────────────────┘
```

签名请求从 A **沿着你来时的那条 SSH 连接**传回你 Mac 的 agent,agent 盖完章再传回去。私钥从没离开你的 Mac,A 上只出现一个临时的"代办窗口"(`SSH_AUTH_SOCK` 指向的通道)。

这就是为什么跳板机场景离不开它:你可以在 A 上再 `ssh B`,B 要的签名照样传回你 Mac——一路跳多少台,钥匙都在家里。

## 6. 三端的 agent 长什么样

| 平台 | agent 从哪来 | 程序怎么找到它 |
|---|---|---|
| macOS | 系统自带(launchd 常驻) | `SSH_AUTH_SOCK` 环境变量指向的 socket 文件 |
| Linux | OpenSSH 的 ssh-agent(桌面环境一般自动启动) | 同上,`SSH_AUTH_SOCK` |
| Windows | OpenSSH 的 ssh-agent 服务(需启动),或 Pageant,或 1Password/Bitwarden 等自带的 agent | 命名管道 `\\.\pipe\openssh-ssh-agent`,或 Pageant 窗口 |

**第三方密码管理器的关系**:1Password、Bitwarden 等都提供自己的 agent(把钥匙存在它们自己的保险库里)。它们的安装步骤都是"把 `SSH_AUTH_SOCK` 指到我的 agent"——所以任何遵守系统约定的程序(包括 zhimaterm)自动就能用上,**不需要任何额外配置**。

## 7. 与 `ssh` 命令的对应速查

熟悉命令行的读者常问"这个开关是不是就是 `ssh -A`",这里把对应关系一次说清
(以 OpenSSH 手册为准):

| zhimaterm | OpenSSH 等价物 | 备注 |
|---|---|---|
| 转发 agent 到远端(会话级,默认关) | `-A` 开 / `-a` 关；配置项 `ForwardAgent yes/no`(默认 no) | 一一对应。`-a` 只是用于覆盖配置或主机别名里的 `yes` |
| 使用本地 ssh-agent(认证素材,默认开) | 默认行为(有 `SSH_AUTH_SOCK` 就用)；关掉等价于配置项 `IdentityAgent none` | **不是 `-a`**——`-a` 管的是"不转发 agent",与"认证时用不用本地 agent"是两件事 |
| 私钥文件 | `-i ~/.ssh/id_ed25519` | 同目录的 `.pub` 会一并使用 |
| 密码 | 无对应 flag(交互输入) | 先试 keyboard-interactive,再试 password |

两个开关互相独立:可以只转发、不参与本机认证之外的任何事,也可以全都不开只用手上的私钥。
另外注意,"远端 agent"并不存在第二个 agent:`-A` 之后 sshd 只在远端会话里放一个 socket,
远端程序连它时,请求沿 SSH 连接回到**本机这一个 agent**——钥匙始终不离开本机。

## 7. zhimaterm 的相关设计(2026-10 共识,详见 ADR)

| 设计 | 内容 | 为什么 |
|---|---|---|
| 认证素材叠加 | agent、私钥文件、密码三者不互斥,按 OpenSSH 顺序尝试(agent → 指定私钥 → 密码),全部失败各自报原因 | agent 是"环境能力"而不是一种"认证方式",对齐 `ssh` 命令的习惯 |
| agent 参与开关 | 连接配置里"使用本地 ssh-agent"开关,默认开 | 本地钥匙多、不想让某台服务器碰它们时可以关掉(等价于 OpenSSH `IdentityAgent none`;注意不是 `-a`,那个是不转发) |
| agent 转发开关 | 会话级勾选,默认关;转发的是"本地 agent 这个环境能力",与认证素材无关。等价于 `ssh -A`(开)/`ssh -a`(关,也是 OpenSSH 默认) | 不用把私钥拷上服务器 |
| 不做地址配置 | 不提供"agent 地址"输入框,靠系统约定自动发现(`SSH_AUTH_SOCK` / Pageant / OpenSSH 管道) | 第三方 agent 都遵守系统约定;找不到时在认证失败信息里说明"未找到本地 agent",而不是含糊的"认证失败" |

zhimaterm 自己**不管理钥匙**(不加载、不存储、不生成),只使用系统里现成的 agent。

## 8. 常见疑问

**Q:私钥会被程序偷走吗?**
不会经由 agent——它只对外提供"签名"服务,任何程序都拿不到私钥本身。但要注意:agent 活着的时候,能用你电脑账号跑起来的程序都可以**请求签名**。所以离开电脑要锁屏;临时不放心可以 `ssh-add -D` 清空 agent 里的钥匙。

**Q:agent 转发安全吗?**
比"把私钥拷到服务器"安全得多(私钥不出门),但也不是零风险:你登录期间,服务器上的 root 理论上可以借用你的转发通道请求签名。所以只在信任的服务器上开,这也是默认关的原因。

**Q:重启后钥匙还在吗?**
macOS:`ssh-add --apple-use-keychain` 之后,口令存在钥匙串里,重启自动恢复。Linux/Windows:默认重启后要重新 `ssh-add`,或用桌面环境的钥匙串集成。

**Q:怎么看我 agent 里有哪些钥匙?**
`ssh-add -l`(列出指纹)。`SSH_AUTH_SOCK` 没设或 agent 没跑会直接报错,这也是第 7 节"报错要说人话"要覆盖的情况。
