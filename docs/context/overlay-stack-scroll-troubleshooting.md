# 排障记录：叠放模态滚动全部失效——同名元素 id 的状态槽冲突

状态：已定位并修复（2026-11-15，叠放规则见 [ADR-044 修订段](../decisions/044-overlay-stack-and-modal-view.md)）。
记录排查路径与 gpui 元素状态索引的关键事实，供以后处理「浮层/复制组件树滚动失效」
类问题时参考。诱因是 WSL 管理从页面改回模态、浮层栈从同物种互斥改为纯叠放——
纯叠放让一直存在的状态槽冲突第一次有了两个受害者。

## 现象

管理模态开着时打开「新增 WSL」（或行内「设置」）——上层模态内容超高被裁，
滚轮完全无效；关掉上层回到管理模态，滚动又正常。单层模态（外壳设置这类）
滚动一直正常。

## 排查链（对照矩阵先锁范围，再取证区分「没派发」与「派发了没生效」）

1. **对照矩阵**：外壳设置模态（单层 Modal）滚动正常 → 全局滚动没坏；管理垫底的
   双层全坏 → 范围锁定「管理模态作底层的双层」。这步排掉了大半候选（本轮改动
   没碰滚动代码、input 单行不注册滚轮的旧修复仍在）。
2. **读派发源码走了一段弯路**：先怀疑滚轮被底层抢走。gpui 的滚轮派发（div.rs
   的 scroll handler + `Hitbox::should_handle_scroll`）语义是：每层滚动容器各自
   在 bubble 注册，`should_handle_scroll` = 指针命中的 hitbox 列表（`mouse_hit_test.ids`）
   包含自己；`occlude()`（`HitboxBehavior::BlockMouse`）会让 hit_test 从最新往回
   收集时**提前 break**——顶层遮罩之下的所有 hitbox 不进列表，底层滚动容器被
   正确排除。结论：派发语义正确，顶层容器应当收到事件。
3. **日志取证**（决定性一步）：给 Card 滚动容器临时挂 `on_scroll` 打印 position
   与 delta，实机双层滚动 → **恰好一条日志**。事件到达了顶层容器、handler 执行、
   偏移已累加——「没派发」被排除，问题在「状态被干扰或重绘不生效」。
4. **最小复现测试**：按 panel::modal 同构搭两层（occlude 遮罩 → overflow_hidden
   面板 → 同名 id 滚动容器 + track_focus + header/actions 兄弟块），模拟滚轮断言
   两层 offset。两个教训：
   - 第一版断言失败，以为是复现成功——实际是指针坐标落在卡片外。合成事件的
     指针坐标必须用 `debug_bounds` 读真实几何校准，不能按窗口尺寸猜。
   - 坐标准确后测试**通过**——纯 gpui 结构复现不出失效。复现不出 + 实机必坏
     → 差异只剩「应用里的两层卡片滚动容器同名 id，且层包装 div 都没有 id」。

## 根因：无 id 的包装层不进元素身份路径，同名滚动容器共享同一个状态槽

gpui 的元素状态（滚动偏移这类存进 element state 的东西）按
`(GlobalElementId, ElementId)` 索引；`GlobalElementId` 只由**带 id 的元素**逐级
贡献路径段。每层模态的包装 div（遮罩、卡片面板）都没有 id，于是两层模态的
滚动容器虽然树位置不同，完整身份路径却相同——**两层的滚动偏移共用同一个槽**：

- 底层 paint 在前，它内容不满、clamp 把共享偏移清零；
- 顶层滚轮 handler 虽然执行了累加，下一帧 paint 时偏移又被底层 clamp 归零——
  表现为「滚了但画面不动」。

互斥替换时代栈上永远只有一个 Modal，`card-content` 全窗唯一，状态独占——
这个坑一直存在，纯叠放让两层同名容器第一次同帧共存，才暴露出来。

## 修复

`OverlayHost::render` 给每层模态根挂唯一 id（`("overlay-layer", index)`）：层
身份路径独立，各层滚动状态各归各槽。返回类型 `Vec<Div>` → `Vec<AnyElement>`
（消费点本来就在做 `into_any_element()`，零适配）。注释写明机制，防止后来人
「顺手去掉这个看似多余的 id」。

## 防复发

- 回归测试 `scroll_goes_to_top_layer_when_stacked`（overlay.rs）：双层叠放 +
  模拟滚轮，断言只滚最上层、底层 offset 不动；与 `layers_stack_and_pop_in_lifo_order`
  （纯栈进出）同守叠放语义。
- 外壳自身的入栈路径（`self.overlay_open` → 无钩子通道）与本修复无关联但同在
  这次排查中核对过：外壳方法里走全局 `overlay_open` 会因入栈钩子嵌套 update
  外壳而 panic（dialog.rs 头注释已有记录）。

## 可复用的诊断方法

- 「滚动完全无效」且已确认 handler 执行 → 不要再查派发，查**状态槽共享**：
  同名 id 的元素 + 无 id 的包装层 = 不同实例共用同一份 element state。
- 叠放、复制、多实例的组件树，**每层根必须带唯一 id**——不管当前有没有状态
  冲突，这是让元素身份路径正确的结构性要求。
- 对照矩阵先锁范围（单层 vs 双层 × 哪个模态），比逐个猜机制快得多；一次
  对照实验排掉的候选，胜过半天源码推理。
- 「没派发」与「派发了没生效」用一条 handler 日志即可区分，这决定了后续
  完全不同的排查方向。
- 合成滚轮测试的指针坐标用 `debug_bounds` 读真实几何校准；坐标错了会得到
  「假复现」或「假通过」，两次浪费都在这上面。
- 读平台源码确认语义（hit_test 的 break、should_handle_scroll 的列表）值得做——
  它把「派发被抢」这条最像真相的死路快速排除，省下的时间给了状态槽方向。
